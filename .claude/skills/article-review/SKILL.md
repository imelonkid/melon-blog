# 文章审阅

审阅 Obsidian `写点东西/` 目录下的博客草稿。**只给建议，不直接改文件**，除非用户明确要求。

## 一、先确定审哪几篇

```bash
cd ~/Workspace/melon-blog && node scripts/review-scan.mjs
```

输出的就是待审文章的完整路径。**不要自己遍历目录**——脚本按正文 SHA-1 比对，
已审过且没改动的会自动跳过，这是"不重复分析"的关键。

- 用户要求全部重审：加 `--all`
- 想看整体状态：`--status`
- 只审某几篇：直接读用户指定的文件，跳过这一步

若输出「没有需要审阅的文章」，如实告诉用户，不要硬找活干。

## 二、逐篇审阅

对每篇文章按下面四类检查。**每条问题都要给出原文和改法**，不要只说"这里可以更好"。

### 1. 错别字

中文高频混淆，逐一核对：

| 易错 | 辨析 |
|---|---|
| 的 / 地 / 得 | 定语用「的」，状语用「地」，补语用「得」 |
| 在 / 再 | 「在」表处所或进行，「再」表重复 |
| 做 / 作 | 具体动作用「做」，抽象搭配用「作」（作出决定、做饭） |
| 像 / 象 | 比喻用「像」 |
| 账 / 帐 | 钱财用「账」，布幔用「帐」 |
| 既 / 即 | 「既然」「既…又」用既；「即刻」「即使」用即 |
| 己 / 已 / 巳 | 自己 / 已经 |
| 需 / 须 | 「需要」用需，「必须」用须 |

技术文另外注意：产品名和术语的大小写（GitHub 不是 Github、JavaScript 不是 Javascript、
MySQL 不是 Mysql、Nginx 不是 nginx 开头句）。

### 2. 语病

- **成分残缺**：主语被介词吞掉（「通过这次实践，使我明白了…」——删「通过」或「使」）
- **搭配不当**：「提高速度」对，「提高效率」对，「提高水平」对，但「提高问题」不对
- **啰嗦**：「进行一个 X 的操作」→「X」；「的的不休」；「其实说实话」
- **语序**：状语位置、多重定语顺序
- **中英混排**：中文与西文之间缺空格（本站惯例是加空格）；全角半角标点混用

### 3. 文笔与风格

这是重点。本站的调性是**克制、具体、有人味**，技术文也一样。判断标准：

**具体物优先于抽象概括。** 这是最重要的一条。
- ✅「相机导出的照片全是 IMG_4821 这种名字，找起来很痛苦」
- ❌「文件命名不规范会影响使用体验」
- ✅「修车铺的师傅收摊前会把工具一件件擦干净」
- ❌「生活中有很多值得留意的细节」

看到抽象概括，就问：能不能换成一个具体的东西、一个时间、一个数字、一个画面？

**技术文要有「人」。** 为什么做这件事、什么地方卡住了、当时什么感受。
纯步骤罗列可以发，但缺一层。开头一句真实的动机往往就够。

**避免 AI 腔。** 这类痕迹要指出来：
- 「首先…其次…最后…」「总而言之」「综上所述」
- 「在当今这个 X 的时代」「随着 X 的不断发展」
- 每段都用破折号做转折，或每段都是三句排比
- 结尾强行升华成人生感悟
- 形容词堆砌而不落到实处（「深刻的」「巨大的」「极其重要的」）

**长短句交错。** 通篇长句会闷，通篇短句会碎。读一遍，把连续三个以上同长度的句子标出来。

**结尾不要用力。** 本站的好结尾是收束而非拔高：
「工具不必大，能省下每次三分钟的翻找，就值得写。」
而不是「让我们一起在技术的道路上不断前行」。

### 4. frontmatter

对照 `src/content.config.ts` 的 schema：

- `title` 必填
- `date` 必填，`YYYY-MM-DD`
- `tag` 建议填，缺失时同步脚本默认给「随笔」
- `publish` 是 `true` 才会被发布——如果用户说"这篇要发了"但字段还是 false，提醒他
- `slug` 决定网址，留空则用文件名（中文文件名会被转成中文网址，能用但不好看，
  技术文建议给英文 slug）
- `excerpt` 留空会自动取正文首段——检查首段是否适合当摘要，不合适就建议手写

## 三、报告格式

每篇一个小节，问题按严重程度排序（错别字/语病在前，风格建议在后）：

```
## 文章标题.md

**错别字**（2 处）
- 第 3 段「他做出了巨大的贡献」→「作出」：抽象搭配用「作」
- 第 7 段「在来一次」→「再来一次」

**语病**（1 处）
- 第 5 段「通过这次排查，让我发现…」：主语被吞。改「这次排查让我发现…」

**风格建议**（按价值排序）
- 第 2 段整段是抽象概括，建议换成具体场景。原文「配置过程比较繁琐」，
  可以写成当时卡了多久、卡在哪一步。
- 结尾「希望这篇文章对大家有帮助」是套话，建议删掉或换成一句自己的判断。

**frontmatter**
- `publish` 仍是 false
```

没问题的篇目也要说一句「未见明显问题」，不要略过——用户需要知道每篇都被看过了。

## 四、审完之后

**先把报告给用户看**，问要不要按建议修改。用户同意后再改文件。

无论是否修改，都要把审过的篇目记录下来，否则下次会重复分析：

```bash
node scripts/review-scan.mjs --mark "文件名1.md" "文件名2.md"
```

**注意**：如果你按建议修改了正文，改完之后再执行 `--mark`——哈希以最终内容为准。

## 边界

- 不要为了凑数而提建议。文章本来就好，就说好。
- 风格建议是建议，用户拒绝就不要坚持。这是他的博客，他的声音。
- 不要把所有文章都改成一个腔调。用户自己的语感（长句、铺陈、由具体景物起兴）
  是特点，不是缺点。
